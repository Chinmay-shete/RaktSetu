Section 0 — Context

What is RaktSetu?

RaktSetu ("Blood Bridge") is India's missing layer between eRaktKosh (government blood search) and hospitals — adding AI forecasting, real-time emergency routing, cross-hospital expiry transfers, and district-level shortage heatmaps.

6 Unique Features Nobody Has Built for India

  • AI Demand Forecasting — ML predicts blood demand per hospital for the next 7 days (Prophet model)
  • Cross-Hospital Expiry Auto-Transfer — blood expiring at A auto-triggers request to hospital B when B is low
  • Emergency Real-Time Routing — fastest path to required blood in a crisis, not a static map
  • Shortage Prediction Heatmap — district officer sees which hospitals/groups go critical in 3–7 days
  • Surgical Schedule → Demand Feed — OT schedule feeds AI forecasting to anticipate surgical blood needs
  • Donor Eligibility Re-Notification — personalised WhatsApp/SMS when 90-day cooldown ends

index.pdf Honest Verdict: What to Build vs What to Skip

Don't waste time rebuilding (already exists):

  • Basic blood stock search — eRaktKosh already does this. Integrate/extend it, don't rebuild it.
  • Donor registration + camp listing — eRaktKosh + BloodConnect both do this. Build it quickly as a base.
  • Nearby blood bank map — Already exists. Build it quickly as base feature, move on.

What makes RaktSetu acquisition-worthy (nobody built this for India):

  • AI demand forecasting + surgical schedule integration — OneBlood (USA) still in research. In India = zero products. This is the acquisition hook.
  • Cross-hospital expiry alert with auto-dispatch — Completely unbuilt in India. 8–10% blood wasted yearly. Saves lives AND money.
  • District-level shortage prediction heatmap — Government doesn't have this. NHM would fund/acquire this directly.
  • Emergency real-time routing — eRaktKosh does basic search but NOT emergency-optimized real-time routing with live confirmation.

6 Unique Features — Detailed Descriptions (From index.pdf)

U1
🤖

AI Demand Forecasting

Uses Prophet/LSTM model trained on surgical schedules + historical transfusion data + seasonal patterns. Predicts how many units of each blood group each hospital will need in the next 7 days. Hospitals pre-order smartly instead of reactively.

U2
🔄

Cross-Hospital Expiry Auto-Transfer

When Hospital A has O– expiring in 24 hrs AND Hospital B is running low on O– → system automatically sends transfer request alert with driver dispatch option and ETA. No human has to notice and call. India loses 8–10% blood to expiry — this fixes it.

U3
🚨

Emergency Real-Time Nearest Blood

Patient or doctor enters blood group + urgency → system queries ALL registered hospitals in real time (not cached data) → shows closest hospital with confirmed live stock, distance, contact → one-tap call to blood bank. Faster than eRaktKosh's manual search.

U4
🗺️

Shortage Prediction Heatmap (District Level)

District health officer sees a live heatmap: which blood groups will hit critical levels in which hospitals in next 3–7 days. Allows proactive camp organisation before shortage hits. Currently officers only know AFTER shortage happens.

U5
🏥

Surgical Schedule → Demand Feed

Planned surgeries for next week fed directly into AI model to improve forecast accuracy. If 15 cardiac surgeries are scheduled next Monday → system pre-alerts blood bank to stock O+ and AB+ in advance. No existing system does this integration.

U6
🔔

Donor Eligibility Re-Notification Engine

Donors who donated 3 months ago are automatically notified when they are again eligible AND when there is a shortage of their blood group within 10 km. Personalised, timely, location-aware. BloodConnect sends generic alerts — RaktSetu's is targeted.

RBAC Middleware (Backend)

const requireRole = (...roles) => (req, res, next) => {
  if (!roles.includes(req.user.role)) {
    return res.status(403).json({ error: 'Insufficient permissions' });
  }
  next();
};

Axios Service Template

// src/services/api.js
import axios from 'axios';

const api = axios.create({
  baseURL: import.meta.env.VITE_API_BASE_URL,
  timeout: 10000,
});

api.interceptors.request.use((config) => {
  const token = localStorage.getItem('raktsetu_token');
  if (token) config.headers.Authorization = `Bearer ${token}`;
  return config;
});

api.interceptors.response.use(
  (res) => res,
  async (err) => {
    if (err.response?.status === 401) {
      localStorage.clear();
      window.location.href = '/login';
    }
    return Promise.reject(err);
  }
);

Section 11 — Open Questions

Unresolved Decisions

25 architectural questions that affect both frontend and backend — must be resolved before backend development begins.

Q1

Single Login Endpoint?

Should there be one /auth/login that returns role in JWT, or separate endpoints per portal? Frontend has 6 login pages currently.

Q2

bloodGroup Format

ProfileSetup stores "A+" but EditProfile displays "O-Positive". Pick one canonical format. Recommended: "O-" short form.

Q3

Who Creates Emergency SOS?

Emergency requests appear in the hospital dashboard. Who creates them? Another hospital, district officer, or an external trigger? Frontend only shows the response side.

Q4

WebSocket vs Polling?

Emergency requests are currently polled every 10s. Should backend support WebSocket or SSE for truly live push? Critical for the emergency dispatch feature.

Q5

Who Sets targetTimestamp?

Emergency SOS countdown uses targetTimestamp (epoch ms). Is this set by the requesting hospital, or computed by the backend on creation?

Q6

status Computed by Backend?

Inventory status ("Expiring Soon", "Low Stock") is currently computed on the frontend. Backend should own this to avoid drift between portals.

Q7

Transfer Direction

Does one hospital create a transfer request that the other receives, or is there a neutral request entity? Frontend shows both Incoming and Outgoing in the same list.

Q8

FundingRecommendations Shape

The /state/funding page exists but no mock data was found in any context file. What object shape does an AI funding recommendation have?

Q9

Feature Flags Persistence

SystemSettings toggles 3 feature flags in React context only (in-memory). Backend needs a persistent store. What 3 flags currently exist and what are their defaults?

Q10

OTP Provider

Firebase for donors (phone OTP). What sends OTP for District Officer login (.gov.in email OTP + phone call)? Firebase doesn't handle email OTP natively.
