The 3-layer architecture — how a FAANG engineer thinks about this
Your system has 3 completely separate concerns. Each layer can fail independently, be replaced, or scaled. Never mix them.
Layer 1Client layer
What users see and touch
  • React web app — hospital dashboard + district officer panel [cite: 109]
  • Flutter mobile app — donor-facing, public emergency search [cite: 110, 111]
  • Both talk ONLY to the REST API. Never touch DB directly. [cite: 109]
Layer 2API + business logic
The brain of the system
  • Node.js + Express REST API — all CRUD, auth, routing [cite: 109]
  • JWT auth middleware — every request verified here
  • Cron job scheduler — runs batch expiration checks every hour [cite: 95]
  • Calls Python AI engine via internal HTTP protocols [cite: 104]
Layer 3AI engine (Python)
Completely separate time-series service
  • Flask API — exposes /predict and /shortage endpoints [cite: 104]
  • Prophet model — trained on historical transfusion data trends [cite: 103]
  • Reads surgical schedules from DB to improve accuracy [cite: 93, 109]
  • Returns JSON predictions — Node.js acts on them [cite: 104]
Storage + services
External dependencies
  • MySQL — split inventory logic (summary counts + granular asset logs)
  • Firebase — real-time push notifications to Flutter mobile clients
  • Twilio & WhatsApp API — automated dispatch alerts and donor communications [cite: 113]
  • Google Maps API — distance matrices, live asset routing [cite: 109, 112]
✨ [ADDED] Idempotency & Fault-Tolerance Architecture Layer
Ensures system stability even if the Python AI model crashes or database connections get bottlenecked.
  • Graceful Forecast Degradation: If the Flask AI endpoint handles an error or drops, Node.js transparently catches the failure and serves cached predictions from yesterday's database sync.
  • Database Connection Pool Overload Protection: Configured Express framework pool connections safely limit concurrent write loads during peak disaster coordination alerts.
FAANG interview answer: "Why this architecture?"
Separation of concerns. The AI engine is an independent microservice — if the ML model needs retraining, you redeploy just Flask without touching Node.js or React[cite: 104, 109]. The DB never speaks to clients. JWT stateless auth scales horizontally. Every layer has exactly one job.

Normalized Production Schema — 7 Core Tables Design
Separating aggregated tracking summaries from granular expiration batch rows prevents data overwrites and ensures cron precision.
hospitals
id INT PK AUTO_INCREMENT name VARCHAR(100) address VARCHAR(255) district VARCHAR(50) lat DECIMAL(9,6) lng DECIMAL(9,6) phone VARCHAR(15) created_at TIMESTAMP DEFAULT NOW()
REORGANIZED blood_stock_summary
Aggregated live counts for lightning-fast UI reads and emergency queries.
id INT PK AUTO_INCREMENT hospital_id INT FK → hospitals.id blood_group ENUM('O+','O-','A+','A-',...) total_available INT DEFAULT 0 updated_at TIMESTAMP DEFAULT NOW() -- UNIQUE KEY (hospital_id, blood_group)
REORGANIZED blood_inventory_batches
Tracks individual items, shelf life records, and precise expiration dates.
id INT PK AUTO_INCREMENT hospital_id INT FK → hospitals.id blood_group ENUM('O+','O-','A+','A-',...) units_in_batch INT NOT NULL status ENUM('available','transferred', 'utilized','expired','spoiled') expiry_date DATE NOT NULL created_at TIMESTAMP DEFAULT NOW()
transfer_requests
id INT PK AUTO_INCREMENT from_hospital INT FK → hospitals.id to_hospital INT FK → hospitals.id blood_group ENUM(...) units INT status ENUM('pending','accepted', 'declined','completed') trigger_type ENUM('auto','manual') created_at TIMESTAMP DEFAULT NOW()
donors
id INT PK AUTO_INCREMENT name VARCHAR(100) phone VARCHAR(15) UNIQUE blood_group ENUM(...) lat DECIMAL(9,6) lng DECIMAL(9,6) last_donated DATE eligible_on DATE -- last_donated + 90 days created_at TIMESTAMP DEFAULT NOW()
surgical_schedules
id INT PK AUTO_INCREMENT hospital_id INT FK → hospitals.id surgery_type VARCHAR(50) count INT scheduled_on DATE created_at TIMESTAMP DEFAULT NOW()
