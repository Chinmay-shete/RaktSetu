🗄️ Entity Relationship Diagram (Core Tables)

hospitals

PK id INT
name VARCHAR, address, district
lat, lng DECIMAL, phone

blood_stock_summary

PK id INT
FK hospital_id → hospitals
blood_group ENUM, total_available INT
updated_at TIMESTAMP

blood_inventory_batches

PK id INT
FK hospital_id
blood_group, units_in_batch, expiry_date
status (available/transferred/utilized/expired)

donors

PK id INT
name, phone (UNIQUE), blood_group
lat,lng, last_donated DATE, eligible_on DATE

transfer_requests

PK id INT
FK from_hospital, to_hospital
blood_group, units, status
trigger_type (auto/manual)

surgical_schedules

PK id INT
FK hospital_id
surgery_type, count, scheduled_on DATE

forecasts (AI)

PK id INT
FK hospital_id, blood_group
forecast_day_1..7 INT, confidence_pct FLOAT

users (RBAC)

PK id INT
email, password_hash, role (donor, staff, admin, district, state, sysadmin)
FK hospital_id (nullable)
⟁ One‑to‑many: hospital → blood_stock_summary, batches, transfers, surgical_schedules. Donor independent but linked via notification logs.

Data flows description:
• Donor → registration data → D1 → notification engine → personalized alerts.
• Hospital staff → batch updates → D2 → expiry watcher → auto transfer request.
• Emergency request → process 3.0 → queries D2 & hospital coordinates → returns real-time nearest stock.
• AI engine reads surgical schedules (D4) and batch consumption logs → stores forecast in D5 → dashboards.
How donor flow connects to ERD & DFD: Donor registration populates donors table, triggers eligibility tracking. "Emergency locator" queries blood_stock_summary and hospitals. Re‑notification engine reads donors.eligible_on + shortage predictions from AI forecasts (DFD process 4). All donor actions are secured via RBAC (users table, role = donor). The DFD level 1 shows exactly how donor requests interact with data stores.
